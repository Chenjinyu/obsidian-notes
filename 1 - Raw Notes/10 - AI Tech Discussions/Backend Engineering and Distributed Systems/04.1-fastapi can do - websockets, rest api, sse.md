FastAPI for SSE example
```python
import asyncio
import json
import random
from fastapi import FastAPI, Request
from fastapi.middleware.cors import CORSMiddleware
from fastapi.responses import StreamingResponse

app = FastAPI(title="Real-Time Sports Scores SSE Server")

# Allow web clients to connect easily
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],
    allow_credentials=True,
    allow_headers=["*"],
    allow_methods=["*"],
)

# Initial live match state
LIVE_MATCHES = [
    {"id": "m1", "home": "Arsenal", "away": "Chelsea", "home_score": 1, "away_score": 1, "minute": 64},
    {"id": "m2", "home": "Lakers", "away": "Celtics", "home_score": 92, "away_score": 88, "quarter": 4, "time": "8:15"},
    {"id": "m3", "home": "Yankees", "away": "Red Sox", "home_score": 4, "away_score": 3, "inning": "Top 7th"}
]

async def score_generator(request: Request):
    """
    Simulates real-time score updates and streams them as Server-Sent Events (SSE).
    """
    try:
        while True:
            # Check if client disconnected to free up server resources
            if await request.is_disconnected():
                print("Client disconnected.")
                break

            # Simulate random live action
            match = random.choice(LIVE_MATCHES)
            
            if match["id"] == "m1":  # Soccer match
                match["minute"] += 1
                if random.random() < 0.15: # 15% chance of a goal
                    scorer = random.choice(["home_score", "away_score"])
                    match[scorer] += 1
            
            elif match["id"] == "m2":  # Basketball match
                if random.random() < 0.70: # High chance of points
                    points = random.choice([2, 3])
                    scorer = random.choice(["home_score", "away_score"])
                    match[scorer] += points
            
            elif match["id"] == "m3":  # Baseball match
                if random.random() < 0.10: # 10% chance of a run
                    scorer = random.choice(["home_score", "away_score"])
                    match[scorer] += 1

            # Format data payload using standard SSE format: 'data: <json_string>\n\n'
            sse_data = f"data: {json.dumps(match)}\n\n"
            yield sse_data

            # Broadcast update every 2 seconds
            await asyncio.sleep(2)

    except asyncio.CancelledError:
        print("Streaming connection cancelled.")

@app.get("/api/scores/live")
async def stream_live_scores(request: Request):
    """
    SSE Endpoint that sets the appropriate headers and streams responses.
    """
    return StreamingResponse(
        score_generator(request),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",  # Disables buffering if behind Nginx
        }
    )

if __name__ == "__main__":
    import uvicorn
    print("Starting Server... Navigate your browser to http://127.0.0.1:8000/api/scores/live")
    uvicorn.run(app, host="127.0.0.1", port=8000)

```

**Yes, exactly! You can use the same FastAPI application, the same Uvicorn server, and the same port for both REST APIs and WebSocket connections.**

You do **not** need separate ports.

For example, if your FastAPI application runs on port `8003`, you can expose:

- `POST http://localhost:8003/messages`
- `GET http://localhost:8003/health`
- `WS ws://localhost:8003/ws`

All three endpoints use **port 8003**.

## 1. FastAPI example: REST API + WebSocket

```python
from fastapi import FastAPI, WebSocket, WebSocketDisconnect
import asyncio

app = FastAPI()


# REST API - HTTP GET
@app.get("/health")
async def health():
    return {"status": "healthy"}


# REST API - HTTP POST
@app.post("/messages")
async def create_message(message: dict):
    return {
        "status": "received",
        "message": message
    }


# WebSocket endpoint
@app.websocket("/ws")
async def websocket_endpoint(websocket: WebSocket):
    await websocket.accept()

    try:
        while True:
            # Receive message from client
            message = await websocket.receive_text()

            print(f"Client sent: {message}")

            # Send message back to client
            await websocket.send_text(
                f"Server received: {message}"
            )

    except WebSocketDisconnect:
        print("Client disconnected")
```

Start the application:

```
uvicorn main:app --host 0.0.0.0 --port 8003
```

Now your application supports both HTTP and WebSocket on port `8003`.

## 2. How can REST and WebSocket share the same port?

Because WebSocket connections typically begin as HTTP requests.

For WebSocket over HTTP/1.1, the client sends an HTTP request requesting a protocol upgrade.

### Architecture

```
                   Client
                      |
                      |
                 Port 8003
                      |
                      v
              Uvicorn Server
                      |
                      v
                FastAPI App
                      |
          +-----------+-----------+
          |                       |
          v                       v
     HTTP Request           WebSocket Request
          |                       |
          v                       v
     @app.get()              @app.websocket()
     @app.post()                   |
          |                       |
          v                       v
     HTTP Response           Persistent Connection
                                  |
                                  v
                           Bidirectional Messages
```

The Uvicorn server distinguishes between regular HTTP requests and WebSocket connections.

### REST API request

```
POST /messages HTTP/1.1
Host: localhost:8003
Content-Type: application/json

{"message": "Hello"}
```

The server returns an HTTP response.

### WebSocket connection request

A typical HTTP/1.1 WebSocket handshake looks like:

```
GET /ws HTTP/1.1
Host: localhost:8003
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: ...
Sec-WebSocket-Version: 13
```

The server responds:

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
```

After the handshake, the connection becomes a persistent WebSocket connection.

Both REST and WebSocket use the same underlying TCP port.

## 3. Does WebSocket use HTTP or TCP?
This is an important system design concept.
WebSocket uses **TCP as its underlying transport**.
For a typical HTTP/1.1 WebSocket connection:
```
REST API:

HTTP
 |
TCP
 |
IP


WebSocket:

WebSocket Protocol
 |
TCP
 |
IP
```

WebSocket initially uses HTTP for its handshake, but after the upgrade, communication uses WebSocket frames rather than ordinary HTTP request-response messages.

For HTTPS and secure WebSockets:

```
REST API:

HTTPS
 |
TLS
 |
TCP
 |
IP


Secure WebSocket:

WSS
 |
TLS
 |
TCP
 |
IP
```

So:

- `http://` → HTTP
- `https://` → HTTP over TLS
- `ws://` → WebSocket
- `wss://` → WebSocket over TLS

**In production, you should generally use HTTPS and WSS.**

## 4. Does each WebSocket connection require its own port?
**No. This is another important distinction.**
Suppose 1,000 users connect to your FastAPI application.
```
Client A ─────┐
              |
Client B ─────┤
              |
Client C ─────┤
              v
         FastAPI Server
           Port 8003
              |
        1000 Connections
```

All clients connect to the same server port.
Each connection is uniquely identified at the TCP level by a combination of:

```
Source IP
Source Port
Destination IP
Destination Port
```

For example:

|Client|Source port|Destination port|
|---|---|---|
|Client A|50123|8003|
|Client B|50124|8003|
|Client C|50125|8003|

All three connections share destination port `8003`, but they are separate TCP connections.
This allows the server to manage many WebSocket clients simultaneously.

## 5. What happens if you deploy FastAPI to AWS ECS?
Given your experience with ECS and Application Load Balancers, consider this architecture:

```
                      Clients
                         |
              HTTPS / WSS (443)
                         |
                         v
                  Application
                 Load Balancer
                         |
                  Listener: 443
                         |
                         v
                 Target Group A
                         |
              +----------+----------+
              |                     |
              v                     v
          ECS Task 1            ECS Task 2
          Port 8003             Port 8003
              |                     |
          FastAPI App           FastAPI App
              |                     |
          +---+---+             +---+---+
          |       |             |       |
         REST     WS           REST     WS
```

Your ALB listens on port `443` for HTTPS and secure WebSocket connections.

It forwards traffic to FastAPI running on port `8003`.

You do not need separate target groups or listeners just because one endpoint uses WebSocket and another uses REST.

<span style="color:red">**One important production consideration:** WebSocket connections are long-lived. If you scale your ECS service to multiple tasks, each task maintains its own WebSocket connections.</span>
For example:
```
                ALB
                 |
        +--------+--------+
        |                 |
        v                 v
    ECS Task A        ECS Task B
        |                 |
    Client 1           Client 3
    Client 2           Client 4
```

If Task A needs to send an event to Client 3, it cannot directly access Task B's in-memory WebSocket connections.
You would typically use <span style="color:red">Redis Pub/Sub, another messaging system, or a shared event distribution mechanism to coordinate across tasks.</span>
OR better way is to separate REST and WebSocket ECS services to different ECS services
```text
                        Clients
                           |
                      HTTPS/WSS
                           |
                           v
                     AWS ALB
                    Listener 443
                           |
                  Listener Rules
                           |
              +------------+------------+
              |                         |
              v                         v
         Path: /api/*              Path: /ws/*
              |                         |
              v                         v
        Target Group A            Target Group B
              |                         |
              v                         v
       ECS REST Service          ECS WS Service
              |                         |
       +------+------+            +-----+-----+
       |             |            |           |
       v             v            v           v
    REST Task 1  REST Task 2   WS Task 1   WS Task 2
       |             |            |           |
    FastAPI       FastAPI       FastAPI     FastAPI
    Port 8003     Port 8003     Port 8003   Port 8003
```

#### How does ALB routing work?

| Priority | Condition             | Action                                     |
| -------- | --------------------- | ------------------------------------------ |
| 1        | Path `/ws` or `/ws/*` | Forward to Target Group B                  |
| 2        | Path `/api/*`         | Forward to Target Group A                  |
| Default  | Everything else       | Return 404 or forward to a default service |

Also configure the ALB idle timeout and application-level heartbeat behavior appropriately for long-lived connections.

## 6. REST vs WebSocket in FastAPI

|Feature|REST API|WebSocket|
|---|---|---|
|FastAPI decorator|`@app.get()`, `@app.post()`|`@app.websocket()`|
|Protocol|HTTP|WebSocket|
|Default port|80 / 443|80 / 443|
|Custom port|8003|8003|
|Connection|Request-response|Persistent|
|Communication|Client-initiated requests|Full-duplex|
|Best use cases|CRUD, authentication, data retrieval|Chat, remote terminal, live collaboration|

### Key takeaway for system design interviews

You can explain it like this:

> FastAPI supports both REST APIs and WebSocket endpoints within the same application. Both can share the same TCP port because the ASGI server, such as Uvicorn, handles HTTP requests and WebSocket connections.
> 
> A WebSocket connection typically starts with an HTTP upgrade handshake. Once established, it becomes a persistent, full-duplex connection.
> 
> In production, I can deploy a single FastAPI application to ECS behind an Application Load Balancer. The ALB handles HTTPS and WebSocket traffic on port 443 and forwards both to the application's port, such as 8003.

**One final point:** Sharing a port doesn't mean sharing a connection. REST requests and WebSocket sessions use separate connections, even though they connect to the same listening port.
