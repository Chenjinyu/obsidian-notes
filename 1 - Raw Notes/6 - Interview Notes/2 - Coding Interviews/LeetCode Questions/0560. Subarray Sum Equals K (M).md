# Problem
Given an array of integers `nums` and an integer `k`, return _the total number of subarrays whose sum equals to_ `k`.
A subarray is a contiguous **non-empty** sequence of elements within an array.

**Example 1:**
**Input:** nums = [1,1,1], k = 2
**Output:** 2

**Example 2:**
**Input:** nums = [1,2,3], k = 3
**Output:** 2

**Constraints:**
- `1 <= nums.length <= 2 * 10^4`
- `-1000 <= nums[i] <= 1000`
- `-10^7 <= k <= 10^7`

# Step 2 - Try Brute Force First to help you understand the structure of the problems
```python
from typing import List

def subarray_sum(nums: List[int], k: int) -> int:
"""
worse case: O(n^2). space compliexity: O(n)
"""
	left = ans = window_sum = 0
	prefix = [0] * (len(nums) + 1)
	for i in range(len(nums)):
		prefix[i+1] = prefix[i] + nums[i]
	
	for j in range(len(nums)):
		# calcuate the current window sum form the prefix array
		window_sum = prefix[j + 1] - nums[left]
		# shrink the window as long as the sum is TOO LARGE
		while window_sum > k and left <= j:
			window_sum -= nums[left]
			left += 1
		# After finish the shrinking, if it exactally equals K, we found the match.
		if window_sum == k:
			ans +=1
	
	return ans
```
1. the solution only works with positive numbers, because it uses a sliding window approach to find subarray, and the sliding window can be shrink by left with checking window_sum > k.
### Step2 - Takeaways
#### Sliding window with "Monotonicity" Requirement
	A variable-side sliding window relies on a concept called "Monotonicity"(meaning it only moves in one direction).
	it assumes two golden rules:
		1. **Expanding** the window (moving right) will always increease (or keep the same) the sum.
		2. **Shrinking** the window (moving left) will always decrease (or keep the same) the sum.
	because of these rules, the algorithm always knows exactally what to do: if the sum is too small, expanding the window, if its too big, shrink the window
SO, NEGATIVE NUMBER Breaks the golden rules.

#### for sliding window, always let the left catch up to close the right. 
#### add a placeholder at the begining of the prefix array to represent the state before the first element. for sum and XORs, the placeholder is 0. For product, the placeholder is 1.  this allows us to calculate subarrays starting at index 0 cleanly without writing messy if left == 0: edge-case logic everywhere

# Step 3 - Think about Optimization
```python
# Using hashmap is the best solution, because it key can store negative number.
# the main idea here is: 
# get prefix. should know: eg. prefix[3] - prefix[1], means the prefix[3] sums up by nums[2] + nums[3]. 
# -2 + 2 + k = k, then  [-2,2,k] is a vaild subarrary
from collections import defaultdict
def subarray_sum_hash_map(nums: List[int], k: int) -> int:
	prefix = defaultdict(int) # or {0:1}
	prefix[0] = 1 # this is the placeholder for e.g. subarrary [-2, 2, 3], and k = 3.
	curr_sum, ans =0, 0
	for i in range(len(nums)):
		curr_sum += nums[i]
		gap = curr_sum - k # gap = nums[j] - nums[i]
		if curr_sum - k in prefix: # use past checkpoint to count subarrays
			ans += prefix[curr_sum - k]
		# stores the left boundary for the left total sum. the total_sum can be any, 
		# e.g. 1, then check future total_sum(4) - k(3) if equals to 1. 
		# e.g. 7, then check future total_sum(10) - k(3) if equals to 7. 
		# means total_sum(10) - left_boundary_sum(7) = k, the sum_of_subarray between 10 and 7, has elements can sum up to k.
		prefix[curr_sum] = prefix.get(curr_sum, 0) + 1 # store current checkpoint for future use
	return ans
		


"""
the key math identity is:
`prefix_sum[j] - prefix_sum[i] = subarray_sum(i+1, j)`.    
then    ---- the prefix_sum[j] - prefix_sum[i] is the gap, and check the gap if equals k ----
prefix_sum[j] - prefix_sum[i] = k 
→ prefix_sum[i] = prefix_sum[j] - k 
→ prefix_sum[i] = cur_sum - k
"""

```

# Step 4 - If stuck > 20 mins, Study the solution
1. Why does the algorithm work?
	```text
	-> Since the elements can be negative and positive. so the sliding window cannot handle the negative element
	-> The hash map stores the left boundary sum with the appeared times. e.g left_boundary = [1](1), or [1, 3, -2, -2](0), [1, 3, -2, -2, 3, -5](-2), these sum of subarray will be counted, if [1,3] - 3 = [1].  [1, 3, -2, -2, 3] - 3 = [1, 3, -2, -2],  [1, 3, -2, -2, 3, -5, 5] - 3 = [1, 3, -2, -2, 3, -5].
	in other words, the [1, 3, -2, -2, 3, -5] is potential a candidate if the next element is 5.
	{1:1, 0:1, -2:1}
	-> why init {0:1} to start: because the subarray starting from index 0 means the left boundary is before the array begins.
	`{0: 1}` represents **one left boundary** — the imaginary checkpoint before index 0, so that subarrays starting at index 0 can be detected.
	When `cur_sum - k = 0` is found at some index `j`, it means:
	prefix_sum[j] - 0 = k
	→ the subarray from index 0 to j sums to k
	Without the seed, that left boundary doesn't exist in the map, and you'd miss every subarray that starts at index 0.

	```
	
2. What pattern is this problem?
```text
	This is the **Prefix Sum + HashMap** pattern.
	## When to recognize it
	- "find number of subarrays that sum to k"
	- "find number of subarrays whose sum equals/divisible by k"
	- You need to count **how many** valid subarrays exist, not just find one
```

3. What problem type does it belong to?
```text
The core idea is always the same — **transform a subarray problem into a checkpoint-gap problem** using prefix sums, then use a hashmap to look up past checkpoints in O(1).
```
